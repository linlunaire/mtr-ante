# 1.21.1 轨道异步上传内存修复

适用范围：YLTE / ANTE 的 Minecraft 1.21.1 Java 分支。不涉及 26.2、MTR 的存档格式或网络协议。

## 报告证据与结论

本次检查依据 `错误报告-2026-10-14_0.20.27.zip` 中的 `debug.log`、`latest.log` 和 `hs_err_pid9300.log`。报告包含 YLTE `1.1.1-1.21.1`、YanlingMTR 1.0.3、NeoForge 21.1.248；没有执行报告中的启动脚本。

- 00:17:20.671 出现传送，约 149 秒后首次发生轨道模型原生分配失败。
- 00:19:49.834 的调用链为 `OffHeapAllocator.allocate → RawMesh._uploadAsync → RawModel.uploadAsync → MeshBuildingRailChunk.rebuildBuffer`。
- 随后出现 NVIDIA OpenGL 的 `GL_OUT_OF_MEMORY`、无效缓冲区范围及 Sodium 的原生缓冲区重新分配失败；最终在渲染线程的 OpenGL 绘制路径发生访问违规。
- 最终快照的 Private Bytes 为 35,899 MiB（约 35.06 GiB），Java 堆使用约 4.22 GiB，堆上限为 26 GiB。Windows 报告该进程可继续提交的额度约为 4 MiB；这不是“分页文件磁盘上只剩 4 MiB”。
- `pool-39-thread-867` 是线程名称中的累计编号，不能据此声称同时存在 867 个线程。最终快照中该池有 57 个线程。

旧源码可以确认无界构建/上传积压、部分分配失败时的泄漏和区块卸载后的旧任务问题。自动故障注入也在旧实现上复现了资源未释放和失效任务仍上传。这些是需要修复的真实缺陷，但报告不能证明全部进程内存由 YLTE 占用，也不能单独归因最终的 OpenGL 访问违规。Roxy/Voxy 的过期结果日志本身不是其内存泄漏的证明。

## 修复范围

- 轨道后台构建最多 2–4 个工作线程，构建队列和上传队列各限制为 32 项。轨道任务另有总计 32 项的准入限制。
- 在复制构建快照或分配原生暂存缓冲区之前预留字节预算，普通任务的总预算为 64 MiB。单个估算超过预算的区块只在其他任务全部排空后独占执行，避免大模型永远无法显示；因此 64 MiB 不是超大单任务的硬上限。
- 每次渲染上传最多执行 4 个任务，并在任务间检查 2 ms 时间预算；单个 OpenGL 调用不能被这个预算中断。
- `PreparedUpload` 明确持有待上传数据：准备失败、取消、上传抛出 Java 异常或重复关闭均有释放路径；成功后 GPU 资源交给使用方，重复取得结果不会再分配一份。
- 网格和模型的部分准备失败清理先前分配的缓冲区。同步模型上传仍逐网格执行，不一次暂存整个模型。
- 区块关闭会失效化当前代次、移除排队工作、协作中断正在构建的工作并丢弃旧上传。正在使用原生缓冲区的工作先退出，再释放，避免取消引入 use-after-free。
- 实例化轨道同样受准入、取消和清理规则约束。上传准备或上传方法抛出 Java 异常时保留旧 GPU 资源，不关闭注册表共享的轨道模型；OpenGL 仅设置错误码的情况见文末验收边界。
- VAO 关闭捕获实际 ID，按渲染队列顺序释放；材质视图共享 VAO 所有权，最后一个视图关闭才删除。批量创建失败会清理已经创建的 VAO。
- 复合模型/网格/VAO 集合关闭时，即使某个成员抛出 Java 异常，也继续尝试其余成员，最后传播清理异常；不能据此保证失败的显卡删除已经成功。
- 分配器增加当前/峰值字节计数。`resize` 先申请、复制，再释放旧块，失败时旧持有者仍可安全清理；成功复制期间会短暂同时持有新旧两块。
- 烘焙入口与变形路径保留各自原有几何阈值，但跳过非有限/非正的有效长度、重复间隔及步长，检查浮点步进是否前进，避免退化输入让循环无法结束。

`RailChunkBase.getAsyncDiagnostics()` 返回工作线程数、构建/上传队列数、预留字节数、正在构建的预留、实际已暂存/排队字节、分配器当前/峰值及超大任务计数。数值是字节；分配器计数仅覆盖经过该分配器的申请，不等于整个进程的堆外内存或显存。

对照测试可在启动器的 JVM 参数中临时加入 `-Dylte.railDiagnostics=true`，让轨道渲染入口每 5 秒把计数写入日志。默认关闭，不持续输出诊断；测试结束可移除此参数。

任务失败保持 dirty 状态，采用 1、2、4、8、16、30 秒退避重试；容量不足在后续帧重试，不丢弃应显示的轨道。取消旧区块不再上传旧资源。

## 自动验证

使用 JDK 21，依赖可用时运行：

```powershell
.\gradlew.bat :common:checkNativeUploadOwnership :common:checkNativeAllocatorAccounting :common:checkVertexArrayOwnership :common:checkCompositeGpuClose :common:checkRailUploadLifecycle --offline --no-daemon --console=plain
```

检查使用真实的网格字节打包、资源所有权、轨道调度及区块生命周期代码，只在 native/GPU/游戏环境边界进行故障注入。覆盖部分分配失败、编码失败、后续网格失败、Java 异常、重复关闭、材质共享视图、取消竞态、实例字节布局、旧资源保留、准入预算、超大任务独占和容量恢复重试。没有在自动检查中创建真实 OpenGL 上下文。

旧实现的失败对照和修复后的结果保存在本地 `build/diagnostics/`；该目录会被 `clean` 删除。新增检查已接入 `:common:check`，发布包仍须通过既有兼容性、脚本、渲染权限和元数据检查。

2026-10-14 本地以 Java 21 / Gradle 8.14.5 执行 `:common:check :fabric:check :neoforge:check --offline --no-daemon`，55 个任务完成，`BUILD SUCCESSFUL`。此次原生上传、分配器、VAO、复合清理、轨道生命周期检查分别通过 338、833、140、50、415 个断言；竞争检查的断言次数可能随线程调度略有变化。日志为 `build/diagnostics/rail-memory-full-check.log`。另以诊断参数启用状态运行轨道检查，通过并输出一次限频计数，见 `rail-diagnostics-enabled-check.log`。

本地候选版本为 `1.1.2-1.21.1`，JAR 位于 `forge/build/libs/YLTE-neoforge-1.1.2-1.21.1.jar` 和 `fabric/build/libs/YLTE-fabric-1.1.2-1.21.1.jar`。核对最终包的修复类存在、Java class major 为 65，且不包含故障注入类；两加载器的包元数据、许可证、旧存档/脚本身份与现有兼容性检查通过。上述检查未替换游戏安装，尚未完成原报告客户端的实机压力对照。

## 游戏内验收与回退

1. 保留旧 JAR，备份存档、配置和资源包，在同一世界的副本中测试；不要同时安装两个 ANTE/YLTE JAR。
2. 保持加载器、其他模组、资源包、视距、JVM 内存设置和传送路线不变。分别以旧版和修复版启动新进程。
3. 连续加载大型铁路场景并往返传送，记录进程 Private Bytes、Windows 提交额度、上述队列/暂存计数；在离开场景和退出世界后等待正在构建的任务结束，再观察暂存是否回落。
4. 检查普通、变形和实例化轨道，列车/脚本模型及材质副本仍正常显示；测试资源重载、退出重进世界和开启原有光影。
5. 若仍崩溃，保留新的 `debug.log`、`latest.log`、`hs_err` 及对应运行时间的计数；恢复旧 JAR 以回退代码。本修复不迁移存档。

真实 `glBufferData` 内存不足可能只设置 OpenGL 错误码，而不抛出 Java 异常。现有异常注入不能证明这种显卡错误已经被捕获并恢复；最终显卡崩溃及 Private Bytes 是否稳定，必须用上述游戏内对照确认。本次没有修改 Windows 虚拟内存、Sodium、Iris 或 Roxy/Voxy 配置。
